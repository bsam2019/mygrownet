# ADR-008: Contract Versioning Strategy

**Status:** Accepted  
**Date:** 2026-07-26  
**Author:** Platform Core Team

## Context

As the platform grows, integration contracts will need to evolve. Some consumers will need time to migrate to new versions. We need a versioning strategy that allows:

- Breaking changes without breaking existing consumers
- Multiple contract versions to coexist
- Consumers to declare their dependency explicitly

## Decision

Contract interfaces are versioned via class name, NOT namespace:

- `InventoryProvider` = v1 (no suffix)
- `InventoryProviderV2` = v2 (suffix for breaking changes)
- `InventoryProviderV3` = v3

### Rules

1. **MAJOR** change (new class name): method signature change, method removal, or semantic behavior change
2. **MINOR** change (same class): adding a new method or optional parameter
3. Old interfaces are annotated with `@deprecated` after replacement is available
4. Providers implement all active versions until consumers migrate
5. Backward-compatibility window: at least one release cycle

### Registry Resolution

The `IntegrationRegistry` resolves the correct version based on which contract class the consumer requests. The `ModuleDiscovery.findByContract()` returns the module that provides a given contract class.

```php
// Consumer requests v1
$v1 = IntegrationRegistry::resolve(InventoryProvider::class);

// Consumer requests v2
$v2 = IntegrationRegistry::resolve(InventoryProviderV2::class);
```

## Consequences

- **Positive:** Clear version contract, easy to audit which consumers use which version
- **Positive:** No namespace renaming needed
- **Negative:** Long interface names (InventoryProviderV2)
- **Trade-off:** Annotating `@deprecated` on the old interface requires discipline
