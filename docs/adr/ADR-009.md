# ADR-009: Event Transport Design

**Status:** Draft  
**Date:** 2026-07-26  
**Author:** Platform Core Team

## Context

When modules are deployed independently (Stage 3+), events must travel across process boundaries. Currently, events are dispatched in-process via Laravel's Event facade. Future independent deployment requires:

- Cross-process event delivery (HTTP, message queue)
- At-least-once delivery semantics
- Subscription discovery (which modules listen to which events)

## Decision

### Phase 1 (Current — Monolith)
Continue using Laravel's in-process `Event::dispatch()`. Writes to outbox table for durability.

### Phase 2 (Extracted Services — Future)
Introduce an event transport adapter layer:

```
Publisher → Outbox → Transport Adapter → Message Queue → Consumer Inbox
```

The `EventSerializer` converts PlatformEvent to a wire format (JSON). Adapters implement a common interface:

```php
interface TransportAdapter
{
    public function publish(PlatformEvent $event, string $queue): void;
    public function subscribe(string $queue, callable $handler): void;
}
```

### Phase 3 (Full Independence)
Use a shared message broker (RabbitMQ or SQS) with:
- One exchange per event type
- One queue per consumer module
- Dead letter exchange for failed events

### Transport Strategies Compared

| Strategy | Latency | Durability | Complexity | Best For |
|----------|---------|------------|------------|----------|
| HTTP sync | Low | Low | Low | Query-style events |
| Message queue | Medium | High | Medium | Financial events |
| Event stream (Kafka) | High | High | High | Audit trails |

## Consequences

- **Positive:** Clear migration path from monolith to distributed
- **Positive:** Outbox/Inbox already implemented — adapters just connect them
- **Negative:** Additional operational overhead for message broker
- **Trade-off:** Choosing a specific broker locks in transport semantics
